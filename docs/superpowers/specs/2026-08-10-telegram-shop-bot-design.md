# Telegram-магазин с настраиваемой админ-панелью — дизайн

Дата: 2026-08-10
Репозиторий: `the-shop-bot-Denis`
Статус: утверждён заказчиком

---

## 1. Задача

Telegram-бот-магазин цифровых товаров по образцу `@bothegreategod_bot`, но с полностью
настраиваемой админ-панелью внутри Telegram. Ключевое требование заказчика: после сдачи
владелец управляет магазином сам, без обращения к разработчику.

Из этого выведено главное архитектурное правило: **ничего, что владелец захочет менять,
не лежит в коде**. Категории, товары, склад, тексты, картинка-шапка, каналы для проверки
подписки, промокоды, администраторы, тайминги — всё в базе, всё редактируется из бота.

## 2. Решения, зафиксированные с заказчиком

| Вопрос | Решение |
|---|---|
| Что такое товар | Склад одноразовых позиций. Одна позиция — произвольный многострочный текст (ссылка, `логин:пароль`, ключ + инструкция). Заливается пачкой, позиции разделены пустой строкой |
| Сервер | Пока нет. Разработка локальная; прод-режим включается переменными в `.env` |
| Секреты | В `.env`, в репозитории только `.env.example` с заглушками |
| Telegram Stars | Не реализуем. Архитектура провайдеров оставляет место под третий способ |
| Валюта | Только рубли. Хранение — копейки, `BIGINT` |
| Проверка подписки | Несколько каналов, список в админке; бот должен быть админом канала |
| Корзина | Один заказ = один товар × N штук (максимум 10) |
| Внутренний баланс | Есть. Возвраты идут на баланс |
| Промокоды | С ограничением области действия (категория/товар) |
| Возвраты | Заменить товар, вернуть деньги, забраковать партию, заблокировать покупателя |
| Многоязычность | Нет. Тексты хранятся по ключам — язык добавляется без переписывания |
| Уведомления | Админам о каждой оплате + выгрузка заказов в XLSX |
| Роли | 👑 Владелец и 🛠 Администратор |
| СУБД | MySQL |
| Redis | Есть: FSM, кеш подписки, очередь рассылки |
| Тексты | Редактируются все |
| Картинка-шапка | Одна на весь бот |
| Изображения товаров | Файл на диске + кеш `file_id` |
| Поиск товара | Есть |
| Лимит покупок на пользователя | Не нужен |
| Миграция данных | Не нужна, старт с нуля |

## 3. Что выяснено про внешние API

### Platega (`https://app.platega.io`)

- Создание платежа: `POST /transaction/process`, заголовки `X-MerchantId`, `X-Secret`.
- Методы оплаты (`paymentMethod`): `2` СБП QR, `3` ЕРИП, `11` карты, `12` международные,
  `13` криптовалюта, `14` SberPay.
- Проверка статуса: `GET /transaction/{id}`.
- Статусы: `PENDING`, `CONFIRMED`, `CANCELED`, `CHARGEBACKED`.
- Callback: `POST` на настроенный в кабинете URL, до 3 повторов с интервалом 5 минут,
  требуется публичный HTTPS с валидным сертификатом.
- Поле `payload` — произвольная строка, кладём туда идентификатор заказа.

**Найденная слабость.** Callback «аутентифицируется» тем, что Platega присылает нам наш же
`X-Secret` в заголовке. Криптографической подписи нет. Любой, кто узнает секрет, сможет
прислать поддельный `CONFIRMED`.

**Следствие для архитектуры:** callback — это только сигнал «сходи проверь». Решение о
выдаче товара принимается исключительно по ответу `GET /transaction/{id}`, с обязательной
сверкой суммы и валюты. Это же закрывает требование ТЗ «не выдавать товар по факту нажатия
кнопки».

### CryptoBot (`https://pay.crypt.bot/api/`)

- Заголовок `Crypto-Pay-API-Token`, есть testnet (`https://testnet-pay.crypt.bot/api/`).
- `createInvoice` умеет фиатные счета: `currency_type: "fiat"`, `fiat: "RUB"` — цены
  остаются рублёвыми, конвертацию делает CryptoBot.
- `getInvoices` — проверка статуса, годится как фолбэк без вебхука.
- Вебхук подписан HMAC-SHA256 по телу запроса, ключ — `SHA256(token)`. Подпись проверяем.

### Telegram Bot API

- Цветные кнопки существуют начиная с Bot API 9.4 (09.02.2026): поле `style` у
  `InlineKeyboardButton` со значениями `primary`, `secondary`, `success`, `danger`.
  Произвольный цвет задать нельзя. aiogram 3.30 поддерживает Bot API 10.2 — доступно.
- Проверка подписки — `getChatMember`; бот обязан быть администратором канала.
- Ограничение частоты рассылки — порядка 30 сообщений в секунду; работаем на 20 с
  обработкой `429 retry_after`.

**Отмечено заказчику как риск, решение принято им:** по Bot Platform Developer ToS
Telegram требует продавать цифровые товары только за Telegram Stars, внешние провайдеры
разрешены для физических товаров. Заказчик выбрал внешние провайдеры.

## 5. Структура

```
bot/
  config.py      — настройки из окружения, ни одного секрета в коде
  db/            — модели и сессии
  repo/          — доступ к данным; SQL живёт только здесь
  services/      — бизнес-правила; не знают про Telegram
  payments/      — провайдеры, поллер, webhook-сервер
  handlers/      — Telegram; не знают про SQL
  keyboards/     — сборка клавиатур, темизация кнопок
  middlewares/   — сессия, пользователь, подписка, троттлинг, ошибки
  scheduler/     — фоновые задания
deploy/          — тест-гейт, проверка миграций
scripts/         — мутационная проверка
tests/
```

Правило слоёв: хендлер не выполняет SQL, сервис не знает про `aiogram`, репозиторий не
принимает решений. Это даёт возможность тестировать бизнес-правила без Telegram.

## 6. Модель данных

Деньги везде — целое число копеек (`BIGINT`). Числа с плавающей точкой в денежных полях
запрещены.

| Таблица | Назначение |
|---|---|
| `users` | `tg_id`, username, имя, первый запуск, последняя активность, блокировка, баланс |
| `admins` | пользователь, роль `owner`/`admin`, кем добавлен |
| `categories` | название, описание, порядок, активность |
| `products` | категория, название, описание, цена, изображение, порядок, активность |
| `stock_batches` | партия завоза: товар, кто залил, количество, заметка |
| `stock_items` | позиция склада: содержимое, статус `available`/`reserved`/`sold`/`defective`, срок резерва |
| `orders` | пользователь, товар, количество, цена до скидки, скидка, итог, промокод, способ оплаты, статус, даты |
| `order_items` | какие именно позиции склада ушли в заказ |
| `payments` | провайдер, идентификатор транзакции, сумма, статус, сырой ответ провайдера |
| `promo_codes` | код, тип и размер скидки, срок, лимиты, минимальная сумма, активность |
| `promo_scopes` | ограничение промокода категорией или товаром |
| `promo_uses` | факт использования: промокод, пользователь, заказ |
| `balance_txns` | леджер движений баланса |
| `texts` | все тексты бота по ключам |
| `settings` | картинка-шапка, тайминги, параметры рассылки |
| `channels` | каналы для проверки подписки |
| `broadcasts` | рассылка и её счётчики |
| `broadcast_targets` | получатели рассылки и результат по каждому |
| `audit_log` | кто из админов что изменил |

Баланс хранится и как леджер (`balance_txns`), и как денормализованное поле
`users.balance_kop`. Леджер — источник правды; поле — кеш, сверяемый тестом.

## 7. Ключевые механизмы

### 7.1 Покупка и выдача товара

```
Купить → резерв позиций → выбор способа оплаты → ссылка → подтверждение → выдача
```

**Резерв.** В одной транзакции создаётся заказ и захватываются N позиций склада запросом
`SELECT ... FOR UPDATE SKIP LOCKED`. Позиции переходят в `reserved` со сроком
`now + N минут` (по умолчанию 20). Если свободных позиций меньше запрошенного — заказ не
создаётся, пользователю показывается фактический остаток.

Это защищает от главной ошибки такого магазина: две параллельные покупки получают одну и
ту же позицию.

**Подтверждение.** Существуют три входа: callback провайдера, кнопка «Проверить оплату»,
фоновый поллер. Все три вызывают одну функцию `confirm_order`, которая:

1. блокирует строку заказа `SELECT ... FOR UPDATE`;
2. если заказ уже `paid`/`delivered`/`refunded` — выходит без действий (идемпотентность);
3. запрашивает у провайдера актуальный статус — **тело callback'а не является основанием**;
4. сверяет сумму и валюту с заказом;
5. только при подтверждённом статусе переводит заказ в `paid`, выдаёт позиции, ставит
   `delivered`.

Один заказ — не более одной выдачи, сколько бы раз функция ни была вызвана и в каком бы
порядке ни пришли события.

**Истечение.** Планировщик раз в минуту освобождает просроченные резервы и переводит
заказы в `expired`.

### 7.2 Оплата с баланса

Тот же путь, но подтверждение мгновенное: списание с баланса выполняется в той же
транзакции, что и перевод заказа в `paid`, с проверкой достаточности средств под
блокировкой строки пользователя.

### 7.3 Возвраты и гарантия

В карточке заказа админу доступны:

- **Заменить товар** — выдать другие позиции взамен, старые пометить `defective`;
- **Вернуть деньги** — сумма зачисляется на баланс покупателя, движение пишется в леджер,
  заказ переходит в `refunded`;
- **Забраковать партию** — все свободные позиции партии переходят в `defective`
  (проданные не трогаются);
- **Заблокировать покупателя** — доступ к магазину закрывается.

Возврат средств на карту через Platega невозможен: в API такого метода нет. Возврат на
внутренний баланс — сознательная замена, согласованная с заказчиком.

### 7.4 Промокоды

Проверяется: активность, срок действия, общий лимит использований, лимит на пользователя,
минимальная сумма заказа, область действия (весь магазин / категория / товар).

Использование фиксируется **только при подтверждённой оплате**. Счётчик увеличивается
запросом `UPDATE promo_codes SET used_count = used_count + 1 WHERE id = ? AND (usage_limit
IS NULL OR used_count < usage_limit)` — атомарно, без гонки на последнем использовании.
Повторное применение к одному заказу закрыто уникальным индексом `(promo_id, order_id)`.

Скидка считается в копейках, итог округляется вниз до целого рубля в пользу покупателя.
Итог не может быть меньше нуля.

### 7.5 Проверка подписки

Middleware на пользовательских хендлерах, кроме `/start` и самой проверки. Для каждого
активного канала выполняется `getChatMember`; положительный результат кешируется в Redis
на 5 минут. Администраторы освобождены.

Отдельно обработан случай, когда бот не администратор канала или канал недоступен: это
ошибка настройки, а не отказ пользователю. Такой канал не блокирует магазин, а порождает
уведомление администраторам. Ложный отказ ломает работу так же, как дыра.

### 7.6 Рассылка

Предпросмотр → подтверждение с числом получателей → постановка задач → воркер. Скорость
по умолчанию 20 сообщений в секунду, `429 retry_after` обрабатывается ожиданием, `403`
помечает пользователя заблокировавшим. Каждый получатель — отдельная строка
`broadcast_targets`, поэтому рассылку можно остановить и продолжить после перезапуска.
Поддерживаются текст, фото+текст, видео+текст и inline-кнопки.

### 7.7 Доступ

Роль читается из базы при каждом обращении, не из токена и не из долгоживущего кеша.
Проверка выполняется на четырёх дверях отдельно: открыть запись, показать список,
выполнить действие, создать. Умолчание — отказ: неизвестное действие запрещено.

Владелец задаётся переменной окружения `OWNER_IDS` и не может быть удалён из админки.

## 8. Оснастка проверки

Перенесена из `HARNESS.md`.

- `deploy/run-tests-gate.sh` — прогон с базовой линией `deploy/test-baseline.txt`;
  блокирует только **новые** падения. Отдельный код возврата `3` для «прогон не
  состоялся»: если интерпретатор не может импортировать pytest, гейт обязан кричать, а не
  рапортовать ноль падений.
- `deploy/check-migrations.sh` — на настоящей MySQL: накат → повтор (no-op) → откат →
  сверка снимка схемы → повторный накат. Сверяются имена и типы всех колонок, индексы и
  внешние ключи, а не их количество.
- `scripts/mutate.py` — мутационная проверка. Запуск запрещён на грязном дереве; исходные
  байты возвращаются из памяти, а не через git; печатается коммит и число найденных
  якорей; отдельный код возврата, если якорь найден ноль или более одного раза.
  Мутации ставятся на четыре места: выдача товара, списание промокода, проверка подписки,
  проверка доступа в админку.

Живая приёмка (после получения доступов): два аккаунта одновременно, реальный платёж
минимальной суммы, сверка суммы с личным кабинетом Platega, проверка повторного нажатия
«Проверить оплату» после успешной выдачи.

## 9. Осознанно не реализовано

- Telegram Stars — по решению заказчика; место в архитектуре оставлено.
- Многоязычность — тексты вынесены в таблицу с ключами, язык добавляется миграцией и
  колонкой, без переписывания хендлеров.
- Корзина из разных товаров — заказ содержит один товар; `order_items` уже позволяет
  расширение.
- Возврат средств на карту — недоступен в API Platega.
